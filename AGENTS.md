# Инструкции для ИИ-агентов

## Проект и источники правил

Это шаблон Symfony 8 / PHP >= 8.4.17 с несколькими bounded contexts, CQRS,
Doctrine ORM 3, PostgreSQL 16, Messenger и Scheduler. Бизнес-модулей и рабочей
токен-аутентификации изначально нет. Namespace приложения — `App\`.

До внесения изменений прочитай [карту модулей](docs/ai/map.md), чтобы определить
владельца кода. Затем перед изменением модуля прочитай `src/<Module>/AGENTS.md`.
Это обязательно и при работе с его тестами вне `src`. Для общей основы прочитай
`src/Shared/AGENTS.md`. Для изменений нескольких модулей прочитай инструкции
каждого.

При создании, изменении или ревью модулей, зависимостей слоёв, публичных
контрактов и конфигурации подключения модулей прочитай
[архитектурные правила](docs/ai/rules/architecture.md).

При создании, изменении или ревью доменных моделей, интерфейсов доступа к данным
и маппинга доменных типов прочитай [правила доменных типов](docs/ai/rules/domain-types.md).

Для репозиториев, DataProvider и коллекций сущностей прочитай
[правила доступа к данным](docs/ai/rules/data-access.md).

Для Command/Query, их обработчиков и доменных Action прочитай
[правила прикладного и доменного поведения](docs/ai/rules/domain-actions.md).

Для межмодульного API и его адаптеров прочитай
[правила контрактов модулей](docs/ai/rules/module-contracts.md).

Для публичных межмодульных событий, их формирования, публикации через outbox
и приёма прочитай [правила межмодульных событий](docs/ai/rules/integration-events.md).

Для API-контроллеров прочитай [правила HTTP-контроллеров](docs/ai/rules/http-controllers.md).

Для начальных dev/test-данных используй [правила фикстур](docs/ai/rules/fixtures.md).

При создании модуля добавь его AGENTS.md по `docs/ai/templates/module-AGENTS.md`.
При добавлении, удалении или переименовании модуля, изменении его назначения
или пути к инструкции обновляй `docs/ai/map.md`.
После завершения работы над каждой задачей, до итогового ответа, сверяй
`docs/ai/map.md` с фактическим состоянием проекта и актуализируй её по результатам
работы.
При изменении границ, инвариантов или публичных контрактов обновляй инструкцию
владельца. Общие правила не копируй в модульные файлы.

## Symfony и данные

Модули подключаются явно в `Kernel::moduleDirectories()`. Конфигурация загружается
в порядке: общая, Shared, модули. В корневом `config/` — только общие настройки.
Сервисы других модулей не переопределять; имена mappings и маршрутов уникальны.
Сущности, value objects и DTO не регистрировать как сервисы.

API-контроллеры находятся в `Presentation/Http/Controller/Api/<Actor>` владельца;
модульные маршруты задают `/api/v1`. Защита `/api` требует
`IS_AUTHENTICATED_FULLY`; закомментированный access_token не является
работающей аутентификацией.

Одна БД, одно подключение и один EntityManager; у каждого модуля своя схема.
Межмодульные ORM-ассоциации, внешние ключи и прямые запросы к чужим таблицам
запрещены. Ссылки передаются как идентификаторы. Изоляция схем логическая,
общие права подключения не обеспечивают физической изоляции.

Команды реализуют Shared Application `CommandInterface`, идут через
`command.bus` с валидацией и транзакцией. Запросы используют `query.bus`
и не изменяют состояние. Внутренние inbox-сообщения реализуют
`InboxMessageInterface`, идут через `inbox.bus` в `async`; после трёх повторов
попадают в `failed`. Это не механизм дедупликации. Технические outbox-сообщения
реализуют `OutboxMessageInterface` и записываются через
`OutboxBusInterface` внутри транзакции команды. Они направляются в отдельные
`outbox.bus` и Doctrine-очередь `outbox`; `make outbox-worker` их обрабатывает.
Запись outbox после commit нарушает атомарность; доставка выполняется после commit.
Публичные события находятся в `Presentation/Contracts/Event/`, не зависят от
транспорта и помещаются в общую техническую обёртку инфраструктурным listener.
Получатели учитывают повторы.

Обработчики Command/Query и внутренних сообщений остаются в Application
и регистрируются в конфигурации модуля с явной шиной. Репозитории не вызывают
flush самостоятельно. Доменные события
реализуют Shared Domain `EventInterface`; их синхронная шина основана на
EventDispatcher. Listener ограничены своим контекстом, выполняются до commit
и не производят внешних побочных эффектов. Прикладные реакции находятся в
Application, адаптация публичных событий — в Infrastructure владельца.
Outbox использует то же подключение
PostgreSQL и таблицу `messenger_messages`; отдельной бизнес-модели в Shared нет.

Ожидаемые доменные исключения наследуют Shared Domain `DomainException`.
HTTP-маппинг задаёт модульный Presentation-провайдер
`DomainErrorProviderInterface`; не добавляй бизнес-ошибки в Shared.
Расписание расширяется инфраструктурными `ScheduleContributorInterface`.

## PHP и окружение

Во всех новых PHP-файлах: `declare(strict_types=1);`, строгие типы,
PHP-атрибуты, constructor property promotion, readonly для неизменяемых
объектов; предпочитай match. Соблюдай `.php-cs-fixer.dist.php`, не меняй vendor.

Основной интерфейс окружения — make:

```text
make start / make start-all / make stop / make logs
make console CMD="debug:router"
make composer CMD="…"
make worker / make outbox-worker / make scheduler
```

Обязательные проверки перед завершением, линтеры, тесты и подготовка тестовой БД
описаны в [правилах проверок](docs/ai/rules/checks.md). Прочитай и выполни эти инструкции
перед завершением работы.

## Безопасность изменений

Не раскрывай .env и секреты. Не отменяй чужие изменения, не выполняй git clean/reset
или автоматические коммиты. Перед добавлением/обновлением зависимостей,
созданием/применением миграций, внешними интеграциями, изменениями окружения
и разрушительными действиями получи согласование, если оно ещё не дано в задаче.
