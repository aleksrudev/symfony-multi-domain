# Инструкции для ИИ-агентов

## Проект и источники правил

Это шаблон Symfony 8 / PHP >= 8.4.17 с несколькими bounded contexts, CQRS,
Doctrine ORM 3, PostgreSQL 16, Messenger и Scheduler. Бизнес-модулей и рабочей
токен-аутентификации изначально нет. Namespace приложения — `App\`.

Перед изменением модуля прочитай `src/<Module>/AGENTS.md`. Это обязательно
и при работе с его тестами вне `src`. Для общей основы прочитай
`src/Shared/AGENTS.md`. Для изменений нескольких модулей прочитай инструкции
каждого. Общее устройство и подключение модулей описаны в `docs/architecture.md`.

При создании модуля добавь его AGENTS.md по `docs/templates/module-AGENTS.md`.
При изменении границ, инвариантов или публичных контрактов обновляй инструкцию
владельца. Общие правила не копируй в модульные файлы.

## Архитектура

Каждый `src/<Module>` — bounded context со своими:

- `Domain` — агрегаты, сущности, value objects, доменные события и исключения,
  интерфейсы репозиториев агрегатов;
- `Application` — сценарии использования, команды/запросы с обработчиками и порты;
- `Contracts` — публичный межмодульный API: интерфейсы и неизменяемые DTO;
- `Presentation` — HTTP-контроллеры и Request/Response DTO, CLI, адаптация входящих
  внешних сообщений;
- `Infrastructure` — Doctrine-репозитории, внешние и межмодульные адаптеры;
- `config` — собственные сервисы, маршруты, mappings и настройки интеграций.

Зависимости: `Presentation -> Application -> Domain`. Infrastructure реализует
порты Application/Domain. Сборка компонентов относится к конфигурации и DI-коду.

Domain не зависит от Symfony и других модулей. Doctrine-атрибуты в сущностях —
единственное намеренное ORM-исключение. Application не зависит от адаптеров;
Validator Constraints допускаются. Контроллеры не вызывают репозитории.

Contracts не раскрывает сущности и не зависит от внутренних слоёв, Symfony
или Doctrine. Чужие Contracts использует только
`Infrastructure/Integration` потребителя через его собственный Application-порт.
Разрешённые зависимости объявляются в `config/dependencies.php` модуля.
Прямые вызовы чужих обработчиков и циклы запрещены.

Shared содержит только технические контракты и механизмы, не бизнес-модели.
Не перемещай туда сущности, бизнесовые value objects, универсальные репозитории
или бизнес-правила ради устранения дублирования.

## Symfony и данные

Модули подключаются явно в `Kernel::moduleDirectories()`. Конфигурация загружается
в порядке: общая, Shared, модули. В корневом `config/` — только общие настройки.
Сервисы других модулей не переопределять; имена mappings и маршрутов уникальны.
Сущности, value objects и DTO не регистрировать как сервисы.

API-контроллеры находятся в `Presentation/Http/Controller/Api` владельца;
модульные маршруты задают `/api/v1`. Защита `/api` требует
`IS_AUTHENTICATED_FULLY`; закомментированный access_token не является
работающей аутентификацией.

Одна БД, одно подключение и один EntityManager; у каждого модуля своя схема.
Межмодульные ORM-ассоциации, внешние ключи и прямые запросы к чужим таблицам
запрещены. Ссылки передаются как идентификаторы. Изоляция схем логическая,
общие права подключения не обеспечивают физической изоляции.

Команды реализуют Shared Application `CommandInterface`, идут через
`command.bus` с валидацией и транзакцией. Запросы используют `query.bus`
и не изменяют состояние. Внутренние inbox-сообщения реализуют
`InboxMessageInterface`, идут через `inbox.bus` в `async`; после трёх повторов
попадают в `failed`. Это не механизм дедупликации.

Обработчики остаются в Application и регистрируются в конфигурации модуля
с явной шиной. Репозитории не вызывают flush самостоятельно. Доменные события
реализуют Shared Domain `EventInterface`; их синхронная шина основана на
EventDispatcher. Обработчики ограничены своим контекстом, выполняются до commit
и не производят внешних побочных эффектов. Outbox пока отсутствует.

Ожидаемые доменные исключения наследуют Shared Domain `DomainException`.
HTTP-маппинг задаёт модульный Presentation-провайдер
`DomainErrorProviderInterface`; не добавляй бизнес-ошибки в Shared.
Расписание расширяется инфраструктурными `ScheduleContributorInterface`.

## PHP и проверки

Во всех новых PHP-файлах: `declare(strict_types=1);`, строгие типы,
PHP-атрибуты, constructor property promotion, readonly для неизменяемых
объектов; предпочитай match. Соблюдай `.php-cs-fixer.dist.php`, не меняй vendor.

Основной интерфейс окружения — make:

```text
make start / make start-all / make stop / make logs
make console CMD="debug:router"
make composer CMD="…"
make lint / make test / make test-unit / make architecture
make worker / make scheduler
make test-db-prepare
```

Unit-тесты изолированы от контейнера и БД. Интеграции с контейнером/БД используют
`Tests\Integration\IntegrationTestCase`; HTTP-тесты — WebTestCase либо прямой
Kernel для проверки адаптеров. Технические fixtures находятся только в tests.

Bootstrap PHPUnit не изменяет БД. `make test-db-prepare` — отдельная явная
подготовка выделенной PostgreSQL БД с суффиксом `_test[TEST_TOKEN]`; команда
не удаляет существующую базу, но применяет миграции, поэтому требует согласования.

Перед завершением запускай релевантные тесты и `make lint`. При изменениях
нескольких слоёв — `make test` и `make architecture`. Для конфигурации также
проверяй контейнер test/prod и Doctrine metadata. Сообщай фактические результаты
и ограничения окружения.

## Безопасность изменений

Не раскрывай .env и секреты. Не отменяй чужие изменения, не выполняй git clean/reset
или автоматические коммиты. Перед добавлением/обновлением зависимостей,
созданием/применением миграций, внешними интеграциями, изменениями окружения
и разрушительными действиями получи согласование, если оно ещё не дано в задаче.
