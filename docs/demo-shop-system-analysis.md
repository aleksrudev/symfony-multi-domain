# Системный анализ: демонстрационный мини-магазин

Статус: проект требований, обновлён 16 октября 2026 года. Документ описывает первую
версию учебного API-бэкенда поверх [архитектурного шаблона](ai/architecture.md).
Реализация и миграции в этот документ не входят.

## 1. Цель и критерий успеха

Приложение должно позволять пройти путь от витрины до подтверждённого заказа и
увидеть, как ограниченные контексты работают отдельно и вместе. Пользователь
должен различать ожидание обработки, бизнес-отказ и технический сбой. Разработчик
должен проследить операцию по одному идентификатору без чтения чужих таблиц из
бизнес-кода. Результат первой версии — JSON API без веб-страниц, фронтенда
и административного UI. Демонстрация выполняется HTTP-клиентом и CLI,
приёмка — HTTP-тестами и интеграционными проверками.

Демо считается успешным, если можно воспроизвести оформление, нехватку остатка,
две конкурентные покупки последней единицы, изменение цены после покупки,
остановку и возобновление worker, повтор сообщения, отмену и истечение срока
резерва. Каждый сценарий должен иметь проверяемый итог в данных и JSON API.

## 2. Участники, границы и допущения

Участники: покупатель, администратор каталога и склада, фоновые worker и
Scheduler. Покупатель видит только свои заказы; администратор может изменять
публикацию/цену товара и складское количество, читать диагностический API.

Первая версия: один магазин, один склад, рубли, целые положительные количества,
фиксированный начальный набор товаров. Товары не создаются через API:
администратор меняет только цену, публикацию и остаток. Корзина — черновик
заказа в `Ordering`; у покупателя одновременно не более одного активного
черновика. После оформления следующий товар попадает в новый черновик.
Оплата, доставка, возвраты, промокоды, внешняя почта,
несколько складов и полноценная учётная система не входят в первую версию.
Наличие и оплата здесь не эквивалентны: `confirmed` означает успешный резерв,
а не оплату.

Для демонстрации уведомлений используется локальный ящик приложения. Это
позволяет проверить их создание и повторы без внешнего сервиса. Защищённый API
требует работающего входа: в первой версии — два покупателя и один администратор
с ролями buyer/admin через Symfony Security и сессии. Учётные данные задаются
настройками окружения; секреты не хранятся в репозитории. Запросы, меняющие
состояние через сессионную аутентификацию, защищаются от CSRF. Публичную
витрину можно читать без входа; корзина и заказы требуют входа. Для этого
правило доступа к `/api` нужно уточнить: чтение витрины, получение состояния
сессии и вход разрешаются до общего правила `IS_AUTHENTICATED_FULLY`.

Технические маршруты входа и выхода принадлежат общей конфигурации
аутентификации, без бизнес-модели пользователя в `Shared`. Анонимный
`GET /api/v1/auth/session` открывает сессию и возвращает CSRF-токен и признак
входа. Клиент передаёт токен в заголовке `X-CSRF-Token` при входе, выходе и
каждом запросе на изменение состояния. После входа клиент повторно получает
состояние сессии и актуальный токен. HTTP-клиент сохраняет cookie в отдельном
cookie jar для каждого пользователя и отправляет его в последующих запросах.
Сессионный cookie имеет `HttpOnly`,
`SameSite=Lax`, а при HTTPS также `Secure`. Идентификатор сессии обновляется
при входе и уничтожается при выходе; попытки входа ограничиваются по частоте.
Пароли пользователей задаются в виде хэшей через переменные окружения.

## 3. Карта контекстов

| Контекст | Владеет | Не владеет |
| --- | --- | --- |
| `Catalog` | карточкой товара, публикацией, текущей ценой | остатком и исторической ценой заказа |
| `Ordering` | корзиной, заказом, снимками позиций, состоянием оформления и отмены | складскими остатками и доставкой уведомления |
| `Inventory` | складскими позициями, резервами и результатами операций | заказом, ценой и покупателем |
| `Notifications` | заданием уведомления, попытками и локальным ящиком | состоянием заказа |

Направление статических зависимостей: `Ordering/Infrastructure/Integration`
использует опубликованные `Contracts` модулей `Catalog`, `Inventory` и
`Notifications`. Остальные три бизнес-модуля друг друга не импортируют.
Адаптеры `Ordering` переводят чужие DTO в собственные типы его Application.
В `config/dependencies.php` модуля `Ordering` перечислены эти три поставщика.
Циклических зависимостей нет. `Shared` остаётся только технической основой.

Каждый модуль владеет своей PostgreSQL-схемой и своим набором миграций.
Общий EntityManager и соединение не дают права делать межмодульные ORM-связи,
внешние ключи или SQL-запросы к чужой схеме. Между контекстами передаются
идентификаторы и копии необходимых значений.

## 4. Предметная модель и правила

### Catalog

`Product` — агрегат с постоянным `productId`, названием, ценой и признаком
публикации. Цена хранится целым числом минимальных денежных единиц, валюта в
первой версии — RUB. Публикацию можно снять, но уже оформленные заказы от этого
не меняются. Контракт `GetOffer` возвращает только опубликованное предложение;
отсутствующий или скрытый товар даёт ожидаемый отказ в оформлении.

### Ordering

`Order` — агрегат с `orderId`, `buyerId`, позициями и состоянием. В черновике
позиция хранит `productId` и количество. Во время оформления она получает
неизменяемый снимок названия, цены и валюты из `Catalog`; итог считается на
сервере. Цена и имя в существующем оформленном заказе не меняются вместе с
каталогом. Пустой черновик и нулевое/отрицательное количество запрещены.
В первой версии заказ можно изменить только в `draft`; после отправки на
резервирование его позиции неизменяемы. Подтверждение требует результата
`reserved` для той же операции. `Order` не хранит сущности других модулей.
Ограничение уникальности в схеме `Ordering` обеспечивает не более одного
`draft` на `buyerId`, в том числе при двух одновременных запросах. Создание
корзины возвращает существующий черновик, если он уже есть; после перехода
в `pending_stock` создание выдаёт новый черновик.

Состояния заказа:

| Текущее | Действие или результат | Следующее |
| --- | --- | --- |
| `draft` | Оформить и записать запрос резерва | `pending_stock` |
| `pending_stock` | Склад зарезервировал всё | `confirmed` |
| `pending_stock` | Склад отказал из-за нехватки | `rejected` |
| `pending_stock` | Покупатель отменил или истёк срок ожидания | `cancelling` |
| `confirmed` | Покупатель отменил или истёк срок резерва | `cancelling` |
| `cancelling` | Склад подтвердил отсутствие резерва | `cancelled` |

`rejected` и `cancelled` — конечные состояния. Повтор уже применённого результата
не меняет заказ. Неизвестный или конфликтующий результат фиксируется как ошибка
обработки; он не должен незаметно подтвердить или отменить заказ. Если склад
сообщил `rejected` после перехода в `cancelling`, заказ ждёт подтверждения
освобождения и затем становится `cancelled`.

### Inventory

`StockPosition` — остаток одного `productId`: `onHand`, `reserved`, доступно
`onHand - reserved`. Увеличение/уменьшение остатка администратором не может
сделать `onHand < reserved`. `Reservation` — результат одной операции по
`orderId`, включающий отсортированный набор позиций и состояние
`pending/reserved/rejected/released`. Одна операция либо резервирует все
позиции, либо не резервирует ни одной. Проверка и изменение затронутых
складских позиций атомарны в транзакции `Inventory`; конкурентные операции
блокируют позиции в одинаковом порядке и не могут зарезервировать больше
доступного. Для нескольких товаров позиции блокируются пессимистически
(`SELECT ... FOR UPDATE` / `LockMode::PESSIMISTIC_WRITE`) в порядке возрастания
`productId`; обработчики резерва и изменения остатка соблюдают один порядок.
Это предотвращает взаимную блокировку заказов с наборами A,B и B,A.
Уникальный `orderId` запрещает второй резерв для того же заказа.

Повтор `Reserve(orderId, items)` с тем же составом возвращает прежний результат;
повтор с другим составом является конфликтом. `Release(orderId)` идемпотентен.
Если освобождение пришло до резервирования, склад сохраняет запись
`released` для `orderId`. Запоздавший `Reserve` после этого не удержит товар.
Записи операций и ключи повторов живут как минимум пока существуют заказы и
возможен повтор из `failed` transport; в демо они не удаляются автоматически.

### Notifications

`Notification` идентифицируется смысловым ключом `orderId + тип события`
(например, `confirmed`, `rejected`, `cancelled`). В первой версии на один
переход нужен один экземпляр уведомления. Повтор задания не создаёт вторую
запись в локальном ящике. Входящее задание сначала сохраняет уведомление
`pending` и локальную задачу доставки в одной транзакции. Задача доставки
обрабатывается отдельно, поэтому сбой не откатывает само уведомление.
При временном сбое доставка повторяется; после исчерпания попыток сообщение
попадает в `failed`, а модуль фиксирует статус `failed` отдельной обработкой
события отказа. Заказ остаётся в своём бизнес-состоянии. В карточке заказа
можно увидеть статус уведомления отдельно от статуса заказа.

## 5. Основные сценарии и границы транзакций

### Оформление

1. Покупатель отправляет черновик на оформление. `Ordering` проверяет владение
   заказом и через свой порт получает предложения `Catalog`.
2. Если хотя бы один товар не опубликован, команда отклоняется без изменения
   состояния и без сообщения в очередь. Снимки цен создаются из предложений,
   полученных в этой операции; возможное изменение цены сразу после чтения не
   переписывает принятый снимок.
3. Команда `Ordering` в одной локальной транзакции сохраняет `pending_stock` и
   исходящее сообщение. Публикация через outbox происходит до commit.
4. Обработчик outbox вызывает опубликованный интерфейс `Inventory.Contracts`.
   Его реализация внутри `Inventory` преобразует DTO контракта во внутреннее
   сообщение и **ставит** запрос резерва в `inbox.bus`. Метод возвращает факт
   принятия в очередь, а не результат резерва, и не меняет складские
   бизнес-таблицы. Отдельный `async`
   worker выполняет команду резерва в транзакции `Inventory` и сохраняет её
   результат в схеме склада.
5. Scheduler `Ordering` выбирает заказы `pending_stock` и читает состояние
   операции через `Inventory.Contracts`. При готовом результате он запускает
   локальную команду перехода. Команда повторно проверяет текущее состояние,
   сохраняет новое состояние и сообщение для `Notifications` в одной транзакции.
6. Обработчик outbox ставит задание уведомления в inbox `Notifications`.
   Получатель сохраняет его в своей транзакции.

Проверка результата складской операции — запрос без побочных эффектов.
До выполнения inbox-сообщения склад может ещё не иметь записи об операции;
контракт возвращает `not_found`, который `Ordering` трактует как ожидание,
а не как отказ. Если запись долго не появляется, действует настроенный срок
ожидания и последующее освобождение с защитной записью `released`.
Интервал проверки по умолчанию: 5 секунд. Это частота, а не обещание задержки:
при остановленных worker или Scheduler заказ остаётся в ожидающем состоянии.
`Ordering` выбирает ограниченную порцию только незавершённых заказов по
индексу состояния и времени следующей проверки. Опрос выбран для первой
версии, чтобы показать Scheduler и сохранить однонаправленный граф
зависимостей. Цена решения — дополнительное чтение и задержка реакции до
очередной проверки. Позднее его можно заменить событием результата резерва,
публикуемым `Inventory` через собственный outbox, сохранив ту же бизнес-модель.

### Отмена и срок резерва

Покупатель может отменить `pending_stock` или `confirmed`. Команда сохраняет
`cancelling` и outbox-запрос `Release(orderId)` атомарно. Склад принимает его
через inbox, выполняет идемпотентное освобождение, а `Ordering` по Scheduler
узнаёт результат через контракт склада и завершает переход в `cancelled`.

Подтверждённый резерв действует 15 минут от момента подтверждения заказа.
Scheduler инициирует ту же отмену по истечении срока. Ожидание резерва дольше
5 минут тоже инициирует отмену. Это значения по умолчанию: сроки ожидания,
резерва и частота проверки задаются конфигурацией; в dev/demo окружении их
можно сократить, например до 30 и 60 секунд. Сроки берутся из времени сервера в UTC.
При одновременной отмене и позднем `reserved` состояние `cancelling` имеет
приоритет; складская запись `released` предотвращает восстановление резерва.

### Изменение данных администратором

Администратор меняет цену/публикацию в `Catalog` и складской остаток в
`Inventory` отдельными командами. Ни одна из этих команд не обновляет
исторические позиции заказов. Отдельного сценария синхронной публикации товара
на склад нет: начальный набор согласованных `productId` создаётся демо-данными.

## 6. Контракты и HTTP-поведение

Публичные межмодульные `Contracts` состоят из интерфейсов и неизменяемых DTO;
в них нет Doctrine-сущностей, Symfony-сообщений и внутренних обработчиков.

| Поставщик | Операция | Вход → результат |
| --- | --- | --- |
| `Catalog` | `GetOffer` | `productId` → опубликованное имя, цена в копейках, RUB или отсутствие предложения |
| `Inventory` | `RequestReservation` | `orderId`, неизменяемые пары `productId/quantity` → принято к асинхронной обработке |
| `Inventory` | `GetReservationResult` | `orderId` → `not_found/pending/reserved/rejected/released`, причина отказа |
| `Inventory` | `RequestRelease` | `orderId` → принято к асинхронной обработке |
| `Notifications` | `RequestNotification` | смысловой ключ, получатель, тип, данные → принято к асинхронной обработке |
| `Notifications` | `GetNotificationStatus` | смысловой ключ → `not_found/pending/delivered/failed` |

`RequestReservation`, `RequestRelease` и `RequestNotification` означают
долговечное принятие задания в очередь, а не завершённое бизнес-действие.
Пока принятое задание уведомления ещё не обработано, `GetNotificationStatus`
возвращает `not_found`, которое диагностический API передаёт как отсутствие
записи о ещё не обработанном задании, а не как окончательный сбой доставки.
Входной DTO склада содержит все данные для резерва и не требует чтения заказа.
Версионированные DTO и типы операций изменяются добавлением полей, совместимым
со старыми сообщениями, либо новым типом сообщения; сообщения в очереди могут
пережить развёртывание. Доменное событие заказа остаётся локальным событием
`Ordering`; наружу передаётся отдельный контракт или запрос по порту.

Предлагаемые маршруты `/api/v1`:

| Метод и путь | Владелец | Результат |
| --- | --- | --- |
| `GET /auth/session` | общая аутентификация | состояние входа и CSRF-токен, доступен анонимно |
| `POST /auth/login` | общая аутентификация | вход по демонстрационным учётным данным; CSRF обязателен |
| `POST /auth/logout` | общая аутентификация | завершение сессии; CSRF обязателен |
| `GET /products` | `Catalog` | постраничная витрина опубликованных товаров |
| `GET /products/{id}` | `Catalog` | карточка товара |
| `PATCH /admin/products/{id}` | `Catalog` | цена и публикация |
| `PATCH /admin/stock/{productId}` | `Inventory` | новый `onHand` при соблюдении резерва |
| `POST /orders` | `Ordering` | новый или существующий активный `draft` покупателя |
| `PUT /orders/{id}/items` | `Ordering` | полная замена позиций черновика |
| `POST /orders/{id}/submission` | `Ordering` | `202`, заказ в `pending_stock` |
| `POST /orders/{id}/cancellation` | `Ordering` | `202`, заказ в `cancelling`, либо текущее конечное состояние при повторе |
| `GET /orders` | `Ordering` | постраничные заказы текущего покупателя |
| `GET /orders/{id}` | `Ordering` | состав, снимки цен, состояние, сроки и причина отказа |
| `GET /admin/notifications` | `Notifications` | постраничный локальный ящик и попытки |
| `GET /admin/diagnostics/orders/{id}` | `Ordering` | объединённая картина заказа, складской операции и уведомлений |

Префикс `/api/v1` задаётся конфигурацией маршрутов модуля. Точные поля
запросов/ответов будут описаны контрактными тестами при планировании, но
обязательные идентификаторы, состояния, суммы в копейках и временные метки
ISO 8601 в UTC определены здесь. Клиент не передаёт итоговую цену заказа.
Списки имеют пагинацию. Создание заказа и его оформление используют стабильный
`Idempotency-Key`, привязанный к покупателю, операции и хэшу запроса: повтор с тем же
телом возвращает тот же заказ/результат, тот же ключ с иным телом даёт `409`.
Ключ атомарно фиксируется с результатом в схеме `Ordering`; параллельный
повтор незавершённой операции получает `202` и адрес статуса заказа.
При новом ключе `POST /orders` всё равно возвращает уже имеющийся активный
черновик. Клиент вызывает создание черновика перед добавлением первого товара.

Ожидаемые ошибки: неверный ввод — `400`/`422`, нет входа — `401`, чужой заказ
или отсутствие записи — `404`, запрещённая роль — `403`, конфликт состояния,
повтор ключа с другим телом или попытка опустить склад ниже резерва — `409`.
Модульные доменные ошибки отображаются через собственные
`DomainErrorProviderInterface` в существующий формат API
`{"text":"...","error":"..."}`. Техническая ошибка не маскируется под
нехватку товара. Ответы не раскрывают секреты или внутренние детали исключений.

## 7. Надёжность и конкуренция

Outbox гарантирует атомарность локальной записи с постановкой исходящего
сообщения в Doctrine-очередь. Worker может доставить сообщение повторно;
`exactly once` не предполагается. `Inventory` защищает резерв уникальностью
`orderId` и проверкой неизменности входных позиций, `Notifications` —
уникальностью смыслового ключа, `Ordering` — допустимыми переходами состояния
и ключом запроса. Дедупликация происходит в той же транзакции, что и изменение
модуля.

Если ответ контракта потерян после принятия запроса, повтор с тем же ключом
безопасен. Если worker или Scheduler остановлены, ожидающие операции остаются
видимыми и завершаются после возобновления. Технические ошибки повторяются
согласно конфигурации Messenger; после трёх повторов сообщение попадает в
`failed`. Администратор видит зависшую операцию, причину и может повторно
запустить обработку через штатный механизм очереди. Бизнес-отказ склада
фиксируется как `rejected`, а не отправляется в цикл технических повторов.

Сбор результатов через Scheduler не требует, чтобы `Inventory` импортировал
`Ordering.Contracts`. Для диагноза обе стороны показывают состояние операции
по одному `orderId`. Запрос диагностики `Ordering` читает собственное состояние
и через свои Application-порты получает представления `Inventory.Contracts` и
`Notifications.Contracts`. Только адаптеры `Ordering/Infrastructure/Integration`
импортируют чужие типы; Query-обработчик не меняет данные. Он собирает
JSON-ответ, не читая чужие таблицы и не выполняя межмодульную запись.

## 8. HTTP API и наблюдаемость

Публичный API каталога возвращает товары и цены. API заказа возвращает снимки
цен, сумму, текущий статус, срок резерва и причину отказа; маршрут отмены
проверяет допустимость действия для текущего состояния. После `202`
HTTP-клиент может опрашивать `GET /api/v1/orders/{id}` с ограниченным сроком
ожидания. Истечение срока опроса означает, что клиент перестал ждать;
оно не меняет состояние заказа. API сохраняет промежуточные статусы без
обещания мгновенного подтверждения. Административные маршруты позволяют
изменить цену, публикацию и складской остаток, прочитать локальный ящик
уведомлений.

Отдельный диагностический API доступен администратору. Он возвращает
переходы заказа, состояние складской операции, статус уведомления и момент
последнего обновления. Состояния строятся из данных владельцев; сообщение
«задание принято» означает постановку в очередь, а не выполнение. Технические
логи содержат `orderId` и идентификатор операции для сопоставления шагов, но
не персональные данные и не содержимое секретов. Ручная имитация сбоя
достигается остановкой worker либо тестовым адаптером уведомлений в dev/test.

`docs/demo-shop-api.md` описывает все маршруты, JSON-поля, роли,
заголовки, пагинацию и ошибки; примеры `curl` используют cookie jar,
CSRF-токен и стабильный `Idempotency-Key`. Документация демонстрации содержит
последовательности HTTP-запросов и ожидаемые ответы для сценариев приёмки.
Разработка страниц и браузерные тесты не требуются.

## 9. Проверяемые требования

| Сценарий | Наблюдаемый итог |
| --- | --- |
| Обычная покупка | Заказ `confirmed`, один резерв на все позиции, одно уведомление |
| Один товар закончился | Заказ `rejected`, ни одна позиция не зарезервирована |
| Два заказа на последнюю единицу | Ровно один резерв успешно создан; доступный остаток неотрицателен |
| Цена изменилась после оформления | Старый заказ сохраняет прежнюю цену, новый использует актуальную |
| Outbox worker остановлен | Заказ остаётся `pending_stock`; после запуска доходит до результата |
| Повтор резервирования/уведомления | Нет второго резерва, второго изменения остатков или дубля письма |
| Отмена во время ожидания склада | Итог `cancelled`, поздний запрос не удерживает остаток |
| Истёк срок резерва | Заказ `cancelled`, товар снова доступен |
| Уведомление не доставляется | Заказ сохраняет бизнес-статус; видны повторы и `failed` |
| Ошибка команды до commit | Нет изменённого заказа и нет соответствующего исходящего сообщения |
| Покупатель запрашивает чужой заказ | Данные не раскрыты, возвращён `404` |
| Два одновременных создания корзины одним покупателем | Возвращается один активный `draft` |
| Запрос на изменение без CSRF-токена | Изменение отклонено; анонимная витрина остаётся доступной |

Unit-тесты проверяют инварианты без контейнера и БД. Интеграционные тесты
проверяют адаптеры и обработчики в выделенной тестовой БД, отдельно —
атомарность outbox и конкурентный резерв в PostgreSQL. HTTP-тесты проверяют
маршруты, роль и владение заказом. Обязательные проверки реализации:
`make lint`, `make test`, `make architecture`, проверка контейнера test/prod и
Doctrine metadata. Подготовка тестовой БД и миграции выполняются только после
отдельного согласования согласно корневому `AGENTS.md`.

## 10. Ограничения и решения для плана

Текущий репозиторий содержит только `Kernel` и `Shared`: бизнес-модули
и аутентификация ещё не реализованы. `Kernel::moduleDirectories()`
пуст; `/api` закрыт правилом `IS_AUTHENTICATED_FULLY`, но рабочий вход не
настроен. В `public/` остаётся точка входа Symfony; HTML/CSS/JavaScript,
Twig и фронтенд-фреймворк для демо не добавляются. Отсутствие UI не меняет
сессионный вход и CSRF-защиту: их использует HTTP-клиент.

При проектировании реализации необходимо уточнить полные JSON-схемы,
команды администрирования, индексы для опроса заказов и точные имена
конфигурационных параметров сроков. Эти вопросы не меняют границы модулей и
описанные бизнес-исходы. Каждому новому
модулю нужен собственный `AGENTS.md` по шаблону и собственная конфигурация.
