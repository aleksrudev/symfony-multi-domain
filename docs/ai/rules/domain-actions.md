# Command/Query как оркестраторы доменного слоя

Применяй при создании, изменении и ревью Command/Query, их обработчиков
и бизнес-операций. В проекте бизнес-операции оформляются как Action —
именованные доменные сервисы в `src/<Module>/Domain/Action/`.

## Application

Command/Query-сценарии в Application — оркестраторы доменного слоя.
Эту роль выполняют их обработчики: организуют последовательность доменных
операций, подготавливают аргументы, передают результаты между Action,
адаптируют итог и взаимодействуют с прикладными портами. Отдельные объекты
сообщений Command и Query остаются неизменяемыми носителями входных данных.

В Application бизнес-модуля разрешены только Command/ и Query/.
Типы группируются по сценарию в `Application/Command/<UseCase>/` или
`Application/Query/<UseCase>/`. В корне сценария находятся только сообщение
Command/Query и его обработчик; остальные типы размещай в подкаталогах
по назначению согласно [структуре сценария](#структура-commandquery-сценария).
Не создавай Application/Message, Application/EventListener, Application/Service
или другие каталоги верхнего уровня в Application. Реализация публичного
межмодульного интерфейса — задача Presentation/Adapter по
[правилам контрактов](module-contracts.md).
Контракты Command/Query находятся в Shared/Application/Bus;
контракт шины доменных событий находится в Shared/Domain/Event.
Назначение паттернов для новых решений определяют
[правила надёжной доставки](transactional-messaging.md).

Тонкость обработчика означает отсутствие собственных бизнес-правил.
Обработчик может вызывать несколько Action и координировать дальнейшие шаги
по их результатам. Бизнес-расчёты, правила допустимости операций и решения
о переходах состояний делегируются доменному слою.

Транзакции, прикладная авторизация, внешние и межмодульные взаимодействия
относятся к прикладной оркестрации и её инфраструктуре.
Внутренние прикладные реакции на доменные факты адаптируют listener из
Infrastructure/Messaging/EventListener/, вызывающие собственный Command/Query.
Оркестрация реакции остаётся в Command/Query handler. Публичный факт формирует
инфраструктурный listener владельца по [правилам межмодульных событий](integration-events.md).
Доставка использует Dispatcher → нейтральный Outbox → Messenger event.bus.
Dispatcher и транспортный адаптер знают протокол, общий механизм Outbox — нет.
Композиция подключена в Shared; фактический состав описан в карте.
Для конкретного исходящего внешнего эффекта допускается инфраструктурный Outbox
по правилам надёжной доставки. Не добавляй универсальную очередь внутреннего
продолжения и транспортную Command только ради асинхронности.

Query не изменяет состояние. Если запрос только выбирает сущности,
обработчик может напрямую вызвать доменный DataProvider и преобразовать
полученные сущности в модели результата Application. Для бизнес-расчёта или проверки доменной доступности
используй Action. Не создавай Action без собственного поведения только
ради перенаправления вызова DataProvider.

## Структура Command/Query-сценария

Правило одинаково для Command и Query: непосредственно в `<UseCase>/`
размещай только `<UseCase>Command.php` или `<UseCase>Query.php`
и `<UseCase>Handler.php`.

| Тип | Каталог внутри сценария |
| --- | --- |
| Дополнительные входные DTO, например элемент списка в Command | `Input/` |
| Главная модель результата сценария и все её вложенные модели | `Result/` |
| Интерфейсы прикладных провайдеров и их собственные модели данных | `Provider/` |

Главный результат также находится в `Result/`, даже если он единственный.
Само сообщение Command/Query остаётся в корне и не переносится в `Input/`.
Модель данных провайдера остаётся в `Provider/`: она описывает данные зависимости,
а не результат сценария. Совпадение её полей с моделью из `Result/`
само по себе не требует объединения этих типов.

Если нужны другие вспомогательные типы, размещай их в подкаталогах по назначению,
не рядом с сообщением и обработчиком. Каталоги создавай только при наличии
соответствующих типов. Для Command без результата не создавай модель результата
или пустой `Result/` ради единообразия.

Пример составного результата Query:

```text
Application/Query/GetOrderDiagnostics/
├── GetOrderDiagnosticsQuery.php
├── GetOrderDiagnosticsHandler.php
├── Result/
│   ├── GetOrderDiagnosticsQueryResult.php
│   ├── OrderDiagnosticResult.php
│   ├── OrderDiagnosticItemResult.php
│   ├── OrderInventoryDiagnosticResult.php
│   └── OrderNotificationDiagnosticResult.php
└── Provider/
    ├── OrderReservationStatusProviderInterface.php
    └── OrderReservationStatus.php
```

## Прикладные провайдеры

Интерфейс получения внешних или межмодульных данных для конкретного сценария
размещай в `Application/Command/<UseCase>/Provider/` или
`Application/Query/<UseCase>/Provider/`. Если провайдеру нужна собственная
модель результата, размещай её в том же `Provider/`, рядом с интерфейсом.
Не размещай эти типы на одном уровне с сообщением и обработчиком сценария
или в общем `Application/Command/Provider/`.

Провайдер описывает потребность прикладной оркестрации и остаётся в Application.
Его инфраструктурная реализация получает данные и преобразует их в собственные
типы потребителя. Для межмодульного взаимодействия следуй
[правилам контрактов](module-contracts.md): только интеграционный адаптер
импортирует публичные Contracts поставщика. Интерфейс провайдера и его модель
результата не зависят от этих Contracts и инфраструктурных реализаций.

Называй интерфейс по предоставляемым сведениям:
`<ПредметноеПонятие>ProviderInterface`, например `ProductOfferProviderInterface`.
Название должно быть понятно потребителю без знания конкретного поставщика.
Имя поставщика или технологии указывай в названии конкретного адаптера,
когда оно помогает отличить реализацию, например `CatalogOfferProvider`.

Модель результата называй по смыслу предоставляемых данных, например
`ProductOffer`. Не добавляй `Snapshot` только из-за неизменяемости объекта
или копирования данных другого модуля. Используй это слово, когда контракт
представляет зафиксированное состояние на определённый момент.
Различай актуальные сведения для выполнения сценария и исторические значения,
зафиксированные доменной моделью. Совпадение полей само по себе не требует
объединять эти типы или создавать отдельный DTO.

Пример размещения типов сценария оформления заказа:

```text
Application/Command/SubmitOrder/
├── SubmitOrderCommand.php
├── SubmitOrderHandler.php
└── Provider/
    ├── ProductOfferProviderInterface.php
    └── ProductOffer.php
```

Прикладной `ProductOffer` содержит актуальные сведения о предложении;
доменный `ProductSnapshot` представляет значения, фиксируемые в заказе.
Модель результата провайдера — неизменяемый объект, не сервис, результат
самого Command/Query-сценария или публичный межмодульный DTO.

## Результаты Query

Результат Query, представляющий одну сущность, список или составные данные,
оформляй отдельной типизированной моделью `<QueryName>Result` в
`Application/Query/<UseCase>/Result/`. Все вложенные модели результата
размещай в том же `Result/`. `GetProductHandler` возвращает
`GetProductQueryResult`, а не `App\Catalog\Domain\Entity\Product`.
QueryResult не должен содержать доменные сущности и их коллекции, включая
вложенные поля и элементы списков. Переноси только необходимые данные
в собственные модели результата; ID и enum преобразовывай в их значения.

Не возвращай структурированные массивы с PHPDoc `array{...}`, `stdClass`
или нетипизированные контейнеры данных. Например, `GetProductsHandler`
возвращает `GetProductsQueryResult` из `Application/Query/GetProducts/Result/`:

```php
final readonly class GetProductQueryResult
{
    public function __construct(
        public string $productId,
        public string $name,
        public int $priceAmount,
        public string $currency,
    ) {
    }
}

final readonly class GetProductsQueryResult
{
    /** @param list<GetProductQueryResult> $items */
    public function __construct(
        public array $items,
        public int $total,
        public int $page,
        public int $limit,
    ) {
    }
}
```

В сигнатуре обработчика указывай конкретный тип результата:
`__invoke(GetProductQuery $query): GetProductQueryResult` или
`__invoke(GetProductsQuery $query): GetProductsQueryResult`.
Обработчик адаптирует доменную `ProductPaginatedCollection`: преобразует
каждый Product из `items` в модель результата, переносит общий `count`
в `total`, добавляет `page` и `limit` из запроса.
Это сборка результата сценария в Application, без новых бизнес-правил.

QueryResult — внутренняя неизменяемая модель Application, а не HTTP Response
или публичный Contracts DTO. Presentation преобразует её в ответ API;
не сериализуй доменные сущности напрямую. QueryResult не регистрируется сервисом.

## Domain

Action выражает конкретную бизнес-операцию и принимает доменные объекты,
value objects, enum и необходимые скалярные значения. Не передавай в него
Application Command/Query, HTTP DTO, Symfony Envelope или чужие Contracts.
Результат Action также не зависит от Application и транспорта.

Action принимает бизнес-решения и вызывает поведение агрегатов. Инварианты
сущности или value object остаются внутри этих объектов и обеспечиваются
при любом способе вызова, включая фикстуры. Не превращай сущность в набор
сеттеров, перенося всю её защиту в Action.

Action может использовать собственные доменные DataProvider и Repository,
когда загрузка и сохранение сущностей нужны для операции. Он зависит только
от их интерфейсов и соблюдает [правила доступа к данным](data-access.md).
Doctrine, EntityManager, flush и управление транзакциями в Action запрещены.
Если доменная операция требует последующих реакций, её Action создаёт и публикует
доменное событие через `App\Shared\Domain\Event\EventBusInterface` по правилам ниже.
Сущностям шину не внедряй. Межмодульная доставка идёт через инфраструктурный
listener владельца и outbox по [правилам межмодульных событий](integration-events.md).
Не импортируй Application, Presentation, Infrastructure, Symfony или другие
бизнес-модули.

Например, обработчик изменения цены передаёт `ProductId` и новую сумму
в `ChangeProductPriceAction`. Action получает товар через DataProvider,
выполняет бизнес-операцию через `Product::changePrice()` и сохраняет через
Repository. Проверка положительной цены остаётся в Product.

Подключай Domain/Action/ узким ресурсом владельца с autowire/autoconfigure;
каждый Action через `Class: ~` не перечисляй. Не сканируй весь Domain.
Action не является обработчиком Messenger
и не получает Symfony-атрибутов регистрации. Обработчики Command/Query
в Application помечаются
`#[AsMessageHandler(bus: 'command.bus')]` с соответствующей явной шиной
по [правилам регистрации](architecture.md#регистрация-сервисов-и-атрибуты).

## Доменные события и реакции

Action публикует событие после успешного изменения агрегата и вызова Repository,
когда операция предусматривает сохранение. Публикация выполняется внутри текущей
транзакции, до commit. Вызов Repository не означает фиксацию транзакции.
При отказе операции событие не публикуется. Повтор команды, обработанный как
идемпотентное воспроизведение результата, не создаёт повторного события.

Доменные события размещай в Domain/Event/. Они реализуют Shared `EventInterface`
и называются по произошедшему факту, например `OrderSubmittedEvent`.
Содержание события определяй смыслом доменного факта независимо от конкретного
listener, outbox-сообщения или внешнего получателя. Не конструируй payload
внутреннего события как копию транспортного DTO.

Внутреннее синхронное событие может содержать ссылку на агрегат. Каждый listener
самостоятельно выбирает необходимые сведения из его доменного API. Объект
события делай final readonly. Время возникновения события передавай явно в
свойстве `eventAt` типа `DateTimeImmutable`: это момент доменной операции,
независимый от времени обработки события и доставки исходящего сообщения.
Например:

```php
final readonly class OrderSubmittedEvent implements EventInterface
{
    public function __construct(
        public Order $order,
        public \DateTimeImmutable $eventAt,
    ) {
    }
}
```

Ссылка на агрегат предоставляет доступ к его текущему состоянию; readonly
не делает сам агрегат неизменяемым. Для исторического снимка состояния нужна
отдельная модель значений. Доменное событие со ссылкой на агрегат используется
только для синхронной обработки внутри своего контекста.

Listener собственных доменных событий размещай в Infrastructure/Messaging/EventListener/.
Он выполняет адаптацию: преобразует событие в собственный Command/Query
и вызывает соответствующую шину либо формирует выбранный публичный факт.
Оркестрацию реакции выполняет прикладной сценарий, бизнесовые решения — Domain.
Listener не вызывает Action, Repository или DataProvider напрямую ради выполнения
бизнесовой реакции. Называй listener по выполняемому действию.
Публикацию публичного события адаптирует инфраструктурный listener владельца по
[правилам межмодульных событий](integration-events.md).
Одно доменное событие может иметь несколько независимых listener.
Подключай их как сервисы владельца с autoconfigure и помечай
`#[AsEventListener(event: OrderSubmittedEvent::class)]` над классом с `__invoke()`.
Не дублируй регистрацию атрибута тегом `kernel.event_listener`.
Это синхронные listener EventDispatcher, а не обработчики Messenger.

При необходимости надёжного внешнего эффекта listener может сохранить
исходящее намерение конкретной интеграции по [правилам Outbox](transactional-messaging.md).
Оно содержит самостоятельные значения, а не агрегаты, сущности или ORM-коллекции.
Доменное событие с агрегатом не передавай напрямую в очередь или другой контекст.
Публичные интеграционные события находятся в Presentation/Contracts/Event/;
их метаданные реализуют читаемый контракт IntegrationEventInterface.
Входящий событийный адаптер извлекает identity и оборачивает собственный
сценарий в нейтральный Consumer. Отдельные Outbox/Inbox DTO на переход не создаются;
протокол событий не проникает в Domain/Application.

Технические Inbox/Outbox-типы внешней интеграции группируются в
`Infrastructure/Messaging/Inbox/<Operation>/` или `Outbox/<Operation>/`.
Файлы непосредственно в Inbox/Outbox не размещай. Не импортируй транспортные
типы в Application и не используй Command/Query как DTO очереди.
Адаптер получателя преобразует входящие значения в собственный сценарий;
он не дублирует оркестрацию и не вызывает доменные операции напрямую.

Listener выполняется синхронно внутри транзакции вызвавшей его команды.
Надёжное исходящее намерение использует то же подключение и фиксируется вместе
с изменениями агрегата. Ошибка listener прерывает команду и откатывает транзакцию;
не подавляй её и не откладывай запись до момента после commit. Listener не вызывает
flush или commit. HTTP-вызовы, отправка писем и другие внешние эффекты выполняются
позднее обработчиками исходящих сообщений.

## Проверка изменений

- Command/Query-обработчики оркестрируют доменные операции; сообщения содержат
  входные данные. В Application нет собственных бизнес-расчётов и правил
  перехода состояний.
- В корне каждого Command/Query-сценария находятся только сообщение и обработчик.
  Дополнительные входные DTO находятся в `Input/`, главный и вложенные результаты
  сценария — в `Result/`, даже при единственной модели результата. Остальные
  вспомогательные типы сгруппированы в подкаталоги по назначению; пустых каталогов нет.
- Прикладные провайдеры и их собственные модели результатов находятся в
  `<UseCase>/Provider/`; названия отражают предоставляемые сведения и отличают
  их от исторических доменных снимков.
- Бизнес-операции находятся в Action; сущности и value objects защищают
  собственные инварианты независимо от Action.
- Query и вызываемые им Action не изменяют состояние и не вызывают запись.
- Результат Query для сущности, списка или составных данных имеет модель `<QueryName>Result`
  и конкретный тип в сигнатуре обработчика; PHPDoc-структура массива её не заменяет.
- Результат не раскрывает доменные сущности напрямую или через вложенные
  объекты и коллекции; преобразование выполняется в Application.
- Action не зависит от прикладных DTO, транспорта и адаптеров, не управляет
  транзакцией и не выполняет внешние побочные эффекты.
- Событие доменной операции публикует Action; его содержание описывает доменный
  факт независимо от listener. Время события имеет имя eventAt.
- Application содержит только Command/Query-сценарии и их собственные типы.
  Listener находятся в Infrastructure/Messaging/EventListener/; технические типы
  внешних интеграций сгруппированы по операциям.
  Адаптер получателя вызывает собственный Command/Query через шину;
  Application не импортирует инфраструктурные сообщения.
  Надёжная запись исходящего намерения выполняется до commit; сообщение
  не содержит агрегат или доменное событие с агрегатом.
- Бизнес-поведение проверяется unit-тестами Action и доменной модели без
  Symfony-контейнера и реальной БД; зависимости от доменных портов заменяются
  тестовыми реализациями. Тесты обработчиков проверяют последовательность вызовов,
  передачу результатов и координацию сценария.
