# Межмодульные события

Прочитай перед созданием, изменением или ревью публичных событий, их
преобразования, публикации через outbox и приёма другим модулем. Границы слоёв
описаны в [архитектуре](architecture.md), общий публичный API — в
[контрактах модулей](module-contracts.md), внутренние события — в
[правилах доменных событий](domain-actions.md#доменные-события-и-реакции).

Это соглашение для новых и изменяемых интеграций. Существующие отступления
и задачи перехода фиксируй в AGENTS.md владельца. Описание целевой архитектуры
не означает, что соответствующие классы и механизмы уже реализованы.

## Владелец и смысл

Событие принадлежит модулю, в котором произошёл опубликованный факт.
Размещай его в `src/<Owner>/Presentation/Contracts/Event/` и называй по факту
в прошедшем времени с суффиксом `Event`, например `OrderSubmittedEvent`.
Названия `Outbox`, очереди, брокера или получателя в имя события не включай.

Контракт выражает факт на языке владельца и документирует его точный смысл.
Например, оформление заказа фиксирует состав и цены и переводит заказ в
ожидание проверки наличия. Решение о резервировании принимает Inventory;
публичное событие Ordering не задаёт ему конкретную команду.
Набор подписчиков определяется конфигурацией интеграций, а не payload.

Внутреннее доменное событие из `Domain/Event/` и публичное событие — разные
контракты. Выбор публикуемых фактов и преобразование задавай явно. Не делай
автоматический экспорт всех доменных событий или сериализацию агрегата целиком.
Одному доменному событию могут соответствовать несколько публичных событий.

## Содержание контракта

Событие и вложенные DTO делай `final readonly`. Допускаются скаляры, `null`
с явно описанным смыслом, собственные публичные DTO и типизированные списки
таких значений. Вложенные DTO размещай в `Presentation/Contracts/Dto/`.
Для структурированных элементов используй отдельные типы, например
`list<SubmittedOrderItem>`, а не `array{productId: string, quantity: int}`.

Публичные типы не зависят от Domain, Application, Infrastructure, Symfony
или Doctrine, включая Shared Application. Они не реализуют внутренние
`EventInterface`, `InboxMessageInterface` или `OutboxMessageInterface`.
Доменные ID и enum преобразуй в значения. Ссылки на сущности, агрегаты,
ORM-коллекции и ленивую загрузку через контракт запрещены.

Выбирай достаточный согласованный набор сведений о факте для задач интеграции.
Не копируй весь агрегат и не добавляй поля без понятного назначения.
Для каждого поля документируй смысл, формат, обязательность, единицы измерения
и допустимые значения. Для списков укажи тип элемента и значимость порядка.

Например, payload `OrderSubmittedEvent` может содержать `orderId`, `buyerId`,
`items: list<SubmittedOrderItem>`, `totalAmount` и `currency`.
`SubmittedOrderItem` содержит `productId` и `quantity`; сумма — целое число
копеек, валюта — согласованный строковый код. Это пример контракта, а не
описание уже существующего публичного API Ordering.

## Формирование снимка

Публичное событие формируется синхронно внутри транзакции операции владельца.
Инфраструктурный listener получает собственное доменное событие и явно
преобразует его сведения в публичные значения. Для синхронного доменного
события со ссылкой на агрегат можно использовать его доменный API в этот момент.
Сформированные DTO не должны сохранять изменяемые ссылки на внутреннюю модель.

Worker доставляет сохранённый снимок. Повторная загрузка агрегата для сборки
payload при доставке может дать состояние другой операции и запрещена.
Время факта `eventAt` переносится из доменного события, а не вычисляется
по времени listener, записи в очередь или работы worker.

Listener выполняет адаптацию без бизнес-расчётов, переходов состояния и вызовов
других модулей для дополнения факта. Если для публикации требуется новое
бизнес-решение, явно моделируй его в Domain/Application владельца.
Отсутствие обязательных данных прерывает публикацию и транзакцию.
Не подставляй вымышленные значения вроде `totalAmount ?? 0` или
`currency ?? Currency::RUB`, скрывающие нарушение инварианта.

## Метаданные и техническая обёртка

Метаданные события отделяются от бизнесового payload и передаются в общей
обёртке. Это часть межмодульного протокола; сохраняй её при доставке до
получателя, а не только в строке outbox.

| Поле | Смысл |
| --- | --- |
| `eventId` | Строковый идентификатор конкретного публичного события, уникальный в пределах `source`. Создаётся один раз при его формировании. |
| `eventAt` | Момент доменной операции: строка RFC 3339 в UTC с шестью знаками микросекунд, например `2026-10-22T09:30:00.123456Z`. |
| `type` | Стабильное логическое имя события, например `ordering.order_submitted`, независимое от PHP namespace и транспорта. |
| `source` | Стабильный идентификатор модуля — владельца факта. |
| `schemaVersion` | Версия публичной схемы payload, изменяемая по правилам совместимости ниже. |

При повторной доставке, восстановлении из failed и доставке разным подписчикам
сохраняй `eventId`, `eventAt`, остальные метаданные и payload исходного события.
Идентификатор строки очереди или отдельной попытки доставки не заменяет
`eventId`. Несколько публичных событий, возникших из одного доменного факта,
имеют собственные идентификаторы.

Реализованный механизм находится в `Shared/Infrastructure/Messaging/`.
`IntegrationEventMetadata` содержит указанные метаданные.
`IntegrationEventEnvelope` реализует `OutboxMessageInterface` и содержит
`metadata`, неизменяемую JSON-строку `payload` и технический `subscriberId`.
Получатель не является частью публичного DTO или метаданных факта.
Shared не импортирует конкретные бизнес-события.
Не создавай для каждого публичного события дополнительный бизнесовый DTO
вида `OrderSubmittedOutboxMessage` только ради этого маркера.
Данные, необходимые для доставки, фиксируются при записи outbox, без ссылок
на агрегаты. Используется существующий сериализатор Messenger: в очереди
остаются только общие технические PHP-типы Shared, метаданные и JSON-снимок.
PHP-классы публичного DTO и вложенных DTO в сообщение очереди не записываются.

## Подключение схем и подписчиков

Кодек публичной схемы принадлежит `Infrastructure/Messaging/Codec/` владельца
и реализует Shared `IntegrationEventCodecInterface`:

- `encode(object $event): string` явно преобразует публичный DTO в JSON-объект
  опубликованной схемы, включая вложенные значения;
- `decode(string $payload): object` валидирует эту схему и восстанавливает
  соответствующий публичный DTO и вложенные DTO. Кодек не выполняет I/O
  и не принимает бизнес-решений.

Регистрируй схему атрибутом на сервисе кодека, например
`#[AsIntegrationEvent(event: OrderSubmittedEvent::class, source: 'Ordering', type: 'ordering.order_submitted', schemaVersion: 1)]`.
Атрибут находится в Shared Infrastructure и не переносится на публичный DTO.
Допустим ровно один кодек для PHP-типа и ровно одна схема для ключа
`source/type/schemaVersion`. Несколько версий логического события используют
собственные публичные PHP-типы и кодеки; сохраняй старые до обработки очередей.

Адаптер подписчика находится в `Infrastructure/Integration/<Owner>/` потребителя.
Например, `#[AsIntegrationEventSubscriber(id: 'inventory.reserve_order', event: OrderSubmittedEvent::class)]`
объявляет постоянный id получателя и публичный PHP-тип события.
Адаптер объявляет публичный нестатический
`__invoke(OrderSubmittedEvent $event, IntegrationEventMetadata $metadata): void`.
Метаданные доступны для идемпотентности и трассировки, а бизнесовый DTO
остаётся независимым от Shared. Один сервис представляет одного подписчика.

Сервисы кодеков и подписчиков загружаются явно или узким ресурсом с autoconfigure.
Теги по этим атрибутам собирает IntegrationEventPass; конфликты схем, id,
неизвестные события и неправильные сигнатуры обнаруживаются при компиляции.
Не дублируй атрибуты YAML-тегами. Общие правила — в
[регистрации сервисов](architecture.md#регистрация-сервисов-и-атрибуты).

## Публикация и транзакция

Listener публикации размещай в
`Infrastructure/Messaging/EventListener/` владельца, например
`PublishOrderSubmittedEventListener`. Он может импортировать собственные
Domain и Presentation/Contracts. Application остаётся независимым от Contracts.
Внутренние прикладные реакции на доменные события остаются в
`Application/EventListener/`, сообщения внутреннего продолжения — в
`Application/Message/`.

Подключай listener как сервис с autoconfigure и предпочтительно помечай
`#[AsEventListener(event: DomainOrderSubmittedEvent::class)]` над классом
с методом `__invoke()`. Он выполняется синхронно до commit, формирует публичный
DTO и вызывает `IntegrationEventPublisher::publish($event, $domainEvent->eventAt)`.
Publisher выбирает кодек по публичному PHP-типу, проверяет JSON-объект,
создаёт общие метаданные и возвращает `IntegrationEventMetadata`.
Он требует активную транзакцию даже при отсутствии подписчиков.

```text
command.bus: начало транзакции
  → Action: изменение агрегата и вызов Repository
  → собственное доменное событие
  → синхронный инфраструктурный listener
  → публичный DTO и IntegrationEventPublisher
  → JSON-снимок, общие метаданные и отдельная обёртка на подписчика
  → все записи Doctrine outbox на том же соединении
commit
  → worker: восстановление DTO и доставка отдельному подписчику
```

Изменения агрегата и запись outbox используют одну транзакцию и то же
Doctrine DBAL connection. Вызов Repository не означает commit. Ошибка маппинга
или записи outbox откатывает изменения агрегата; последующая ошибка команды
до commit откатывает уже записанное сообщение. Не подавляй эти ошибки,
не вызывай из listener flush/commit и не откладывай запись outbox до after-commit.

Внешние эффекты и доставка другим модулям выполняются после commit.
Не вызывай потребителя в транзакции публикации. Каждый получатель обрабатывает
событие в собственной транзакции и учитывает повторную доставку.
Идемпотентное воспроизведение результата команды не создаёт нового события.

Набор подписчиков фиксируется при публикации. Publisher записывает отдельное
сообщение на каждого через существующий OutboxBusInterface в одной транзакции.
Публикация без подписчиков допустима и возвращает метаданные, но записей
очереди не создаёт. Добавление подписчика не доставляет ему историю.

IntegrationEventHandler помечен `#[AsMessageHandler(bus: 'outbox.bus')]`.
Он находит схему по сохранённым source/type/schemaVersion, восстанавливает DTO
и вызывает только сохранённый subscriberId. Неизвестный получатель, схема
или некорректный payload приводят к UnrecoverableMessageHandlingException
и failed без бесполезных повторов. Исключения самого подписчика сохраняют
обычную retry-семантику Messenger. При временных сбоях действуют три повтора.
Повтор не создаёт новые сообщения для уже успешных подписчиков.

Shared не реализует дедупликацию бизнесовых эффектов. Потребитель выбирает
смысловой ключ либо использует `(source, eventId)` в своей области обработки
и фиксирует эффект и отметку обработки атомарно. Повтор одного сообщения
после сбоя worker возможен и при успешном выполнении обработчика.

Потребитель объявляет владельца в `config/dependencies.php`. Чужое событие
импортирует только его `Infrastructure/Integration/<Owner>/`, преобразуя
контракт в собственную Command или inbox DTO и вызывая соответствующую шину.
Application и Domain потребителя не зависят от публичного типа поставщика.
При независимых подписчиках изолируй их доставку: ошибка одного не должна
повторно выполнять уже завершённые эффекты другого. Общие правила транспорта
и повторов находятся в [архитектуре](architecture.md#исходящие-сообщения).

## Совместимость и проверки

Изменение смысла или типа поля и удаление поля требуют новой версии схемы
и согласованного перехода получателей. Для добавления поля проверь чтение
старых сообщений новым кодом и, если версии работают одновременно, новых
сообщений старым кодом. Новый DTO не должен требовать отсутствующее поле
из сообщения, которое уже лежит в outbox, async или failed.

Не связывай `type` с PHP class name: переименование класса не меняет смысл
факта, но требует учесть способ сериализации уже сохранённых сообщений.
Само наличие `schemaVersion` не реализует совместимость; поддержка версий,
сериализация и срок сохранения старых схем описываются явно в AGENTS.md владельца.
Автоматический экспорт DTO через PHP serialization не заменяет публичную схему.

Следуй [проверкам межмодульных событий](checks.md#межмодульные-события).
В AGENTS.md владельца указывай опубликованные и потребляемые события, поля
и метаданные контрактов, listener и регистрацию, подписчиков, ключи
идемпотентности и поддерживаемые версии. Общие правила в модульные инструкции
не копируй.
