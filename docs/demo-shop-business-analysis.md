# Бизнес-анализ: демонстрационный мини-магазин

Статус: проект требований, обновлён 16 октября 2026 года. Этот документ описывает
предметную задачу и ожидаемое поведение первой версии. Технические границы,
контракты и проверки описаны в [системном анализе](demo-shop-system-analysis.md).

## 1. Контекст и цель

В репозитории есть архитектурный шаблон, но нет бизнес-приложения. Поэтому
новому разработчику трудно увидеть, зачем нужны отдельные контексты, как
заказ проходит через них и что происходит при задержке или повторе операции.

Цель демо — дать API-бэкенд небольшого магазина, в котором можно самостоятельно
пройти путь покупки HTTP-запросами и наблюдать его шаги в JSON-ответах.
Веб-страницы, фронтенд и административный UI не входят в первую версию.
Приложение должно показывать два важных
факта: принятие заказа ещё не означает наличия товара, а подтверждение заказа
означает резерв товара, не оплату. Демо предназначено для обучения и оценки
архитектуры. Оно не имитирует выручку, конверсию или промышленную нагрузку.

Результат полезен, если пользователь HTTP-клиента без чтения кода понимает, почему заказ
ожидает обработки, подтверждён или отклонён, а разработчик может воспроизвести
эти исходы и объяснить ответственность каждого контекста.

## 2. Заинтересованные стороны и роли

| Роль | Задача | Доступ |
| --- | --- | --- |
| Посетитель | Получить товары и цены | Публичный API каталога |
| Покупатель | Собрать и оформить заказ, получить итог, отменить заказ | API собственной корзины и собственных заказов |
| Администратор | Изменить цену, публикацию и остаток; получить уведомления и ход операций | Административный и диагностический API |
| Разработчик или демонстратор | Показать успешный путь, нехватку, повторы и восстановление | Тестовые данные, диагностический API и инструкции HTTP-запросов и запуска |

В первой версии минимум три демонстрационных пользователя: два покупателя для
сценария конкурентной покупки и администратор. Разработчик может работать под
ролью администратора. Отдельного рабочего места
оператора склада и отдельной учётной системы нет.

## 3. Бизнес-объекты и словарь

| Термин | Значение для пользователя |
| --- | --- |
| Товар | Предложение магазина с названием и текущей ценой |
| Публикация | Разрешение показывать товар в витрине и принимать новые заказы на него |
| Корзина | Изменяемый черновик заказа покупателя |
| Позиция заказа | Купленный товар, количество, название и цена, зафиксированные при оформлении |
| Остаток | Физическое количество товара в единственном учебном складе |
| Доступно | Остаток за вычетом действующих резервов |
| Резерв | Временно отложенное количество товара под конкретный заказ |
| Подтверждённый заказ | Заказ, для которого склад зарезервировал все позиции |
| Отклонённый заказ | Заказ, для которого склад не смог зарезервировать все позиции |
| Уведомление | Запись в локальном ящике о результате заказа или отмене; это не отправка письма |

Слово «цена» в витрине означает текущую цену, а в заказе — цену на момент
оформления. Эти значения могут различаться. Деньги хранятся и рассчитываются
целым числом копеек и передаются через API вместе с валютой RUB.
Витрина означает публичные данные каталога, корзина — доступный через API
черновик заказа; эти термины не предполагают наличия страниц.

## 4. Целевой процесс покупки

1. Посетитель просматривает опубликованные товары. Для покупки входит под
   учётной записью покупателя.
2. Покупатель создаёт корзину, меняет количество или удаляет позицию.
   До оформления это черновик без гарантии наличия и цены.
3. Покупатель отправляет корзину на оформление. Магазин проверяет, что все
   товары ещё продаются, фиксирует названия и цены, рассчитывает итог.
4. API возвращает идентификатор заказа и статус `pending_stock`
   («Проверяем наличие»). Покупатель может позже запросить заказ по этому
   идентификатору и получить сохранённое состояние.
5. Если склад зарезервировал все товары, заказ становится «Подтверждён».
   Покупатель видит срок действия резерва. Если хотя бы одного товара не хватило,
   заказ становится «Отклонён» с причиной; частичного подтверждения нет.
6. Информация о результате появляется в локальном ящике уведомлений.
   Проблема с уведомлением не меняет результат покупки.

Время между шагами 4 и 5 зависит от фоновой обработки. API возвращает
промежуточный статус; принятие запроса не обещает мгновенного подтверждения.

У покупателя одновременно не более одной активной корзины (`draft`). После
отправки на оформление она становится заказом в обработке и перестаёт быть
корзиной. При следующем добавлении товара покупателю создаётся новый черновик.

## 5. Другие бизнес-сценарии

### Управление товаром и остатком

Администратор меняет текущую цену или снимает товар с публикации. Изменения
влияют на новые оформления и не переписывают старые заказы. Администратор
меняет количество на складе; его нельзя опустить ниже уже зарезервированного.
В первой версии исходный набор товаров фиксирован в демо-данных.

### Отмена

Покупатель может отменить заказ в ожидании склада или после подтверждения.
До завершения освобождения товара он видит «Отменяем». После этого заказ
становится «Отменён», а товар снова доступен. Отклонённый заказ уже завершён
и не требует отмены. Поздний ответ склада не может снова подтвердить заказ,
который находится в отмене.

### Истечение срока

Если склад не завершил проверку за 5 минут, начинается отмена ожидающего
заказа. Подтверждённый резерв действует 15 минут с момента подтверждения;
затем начинается та же отмена. API заказа возвращает срок резерва. Это
значения по умолчанию; для показа и тестов сроки настраиваются отдельно,
например 30 секунд ожидания склада и 60 секунд резерва. Демонстрация
истечения срока использует настроенное значение.

### Восстановление после сбоя

При остановке фоновой обработки заказ остаётся с видимым статусом ожидания.
После восстановления обработка продолжается. Повтор того же запроса не должен
создать второй резерв, второй заказ при повторе оформления или дубликат
уведомления. Техническая ошибка видна администратору отдельно от бизнес-отказа
«Недостаточно товара».

## 6. Бизнес-правила

| ID | Правило |
| --- | --- |
| BR-01 | Купить можно только опубликованный товар. |
| BR-02 | Количество каждой позиции — положительное целое число; пустой заказ оформить нельзя. |
| BR-03 | Название и цена каждой позиции фиксируются при оформлении и не меняются вслед за витриной. |
| BR-04 | Итог заказа рассчитывает приложение из зафиксированных цен и количеств. |
| BR-05 | Заказ подтверждается только после резерва всех позиций; частичное резервирование недопустимо. |
| BR-06 | Доступное количество товара не может стать отрицательным даже при одновременных покупках. |
| BR-07 | Один заказ может удерживать не более одного действующего резерва. |
| BR-08 | Подтверждённый заказ означает резерв, но не оплату или доставку. |
| BR-09 | Покупатель видит и отменяет только собственные заказы. |
| BR-10 | Отмена завершается после освобождения резерва либо подтверждения, что его нет. |
| BR-11 | После начала отмены поздний результат резервирования не подтверждает заказ. |
| BR-12 | Подтверждённый резерв действует 15 минут; ожидание склада длится не более 5 минут до начала отмены. |
| BR-13 | Сбой уведомления не отменяет бизнес-результат заказа. |
| BR-14 | Повтор одной операции не меняет результат и не создаёт дубли. |
| BR-15 | Скрытие товара и изменение его цены не меняют уже оформленные заказы. |
| BR-16 | У покупателя одновременно не более одной активной корзины; после её оформления следующий товар добавляется в новый черновик. |

## 7. Функциональные требования первой версии

| ID | Приоритет | Требование | Проверка через HTTP API |
| --- | --- | --- | --- |
| F-01 | Обязательно | Получать опубликованные товары и цены | Анонимный запрос возвращает постраничный каталог |
| F-02 | Обязательно | Войти как покупатель или администратор | Доступ к заказам и управлению зависит от роли |
| F-03 | Обязательно | Создать и менять корзину | Количества и состав видны до оформления |
| F-04 | Обязательно | Оформить заказ и получить его номер | Сразу виден статус ожидания |
| F-05 | Обязательно | Получить собственные заказы, состав, стоимость и статус | Повторный GET возвращает сохранённое состояние |
| F-06 | Обязательно | Получить подтверждение либо понятный отказ по остатку | Покупатель видит только полное подтверждение или полный отказ |
| F-07 | Обязательно | Отменить ожидающий или подтверждённый заказ | Видны «Отменяем» и конечный статус |
| F-08 | Обязательно | Автоматически освободить истёкший резерв | Статус меняется без действий покупателя |
| F-09 | Обязательно | Изменить цену, публикацию и остаток под ролью администратора | Новые заказы используют новое предложение |
| F-10 | Обязательно | Предоставить API локального ящика уведомлений | JSON содержит результат и состояние доставки |
| F-11 | Обязательно | Предоставить диагностический API конкретной операции администратору | JSON содержит шаги заказа, склада и уведомления |
| F-12 | Желательно | Подготовить воспроизводимые демонстрационные сценарии | Каждый сценарий выполняется HTTP-клиентом по инструкции |

Требования со статусом «Обязательно» составляют минимально законченную версию.
F-12 относится к способу демонстрации, но особенно полезно при оценке шаблона.

## 8. Данные, безопасность и качество API

Для покупателя достаточно идентификатора, необходимого для владения заказом.
Демо не требует адреса доставки, телефона или платёжных данных. Уведомление
появляется в локальном ящике; внешняя почта не используется. Пароли и другие
секреты не отображаются в диагностике и не входят в демо-данные репозитория.

Промежуточные статусы должны отличаться от конечных. Покупатель должен видеть
причину бизнес-отказа и срок резерва, когда они известны. Администратор должен
видеть технический сбой как технический сбой, а не как отсутствие товара.
Список товаров и заказов должен оставаться удобным при росте количества записей
за счёт пагинации API.

Время подтверждения не нормируется как SLA: его определяют скорость фоновой
обработки и доступность компонентов. Для демо важнее сохранить операцию и
показать её текущее состояние, чем скрывать задержку.

## 9. Сценарии приёмки

| ID | Условие | Ожидаемый результат |
| --- | --- | --- |
| A-01 | Достаточно всех товаров | Заказ подтверждён; зарезервированы все позиции |
| A-02 | Не хватает одной позиции | Заказ отклонён; ни одна позиция не удержана |
| A-03 | Два покупателя одновременно берут последнюю единицу | Подтверждается один заказ, второй отклоняется |
| A-04 | Цена изменилась после оформления | В старом заказе прежняя цена; на витрине и в новом заказе новая |
| A-05 | Остановка и запуск фоновой обработки | Сначала ожидание, затем корректный результат без повторного оформления |
| A-06 | Покупатель отменяет подтверждённый заказ | Товар освобождён, заказ отменён |
| A-07 | Покупатель отменяет заказ до ответа склада | Итог — отмена, запоздавший резерв не удерживает товар |
| A-08 | Прошёл настроенный срок резерва (по умолчанию 15 минут) | Началась отмена, затем товар стал доступен |
| A-09 | Повторяются создание и оформление заказа либо сообщения | Нет дополнительного заказа, резерва или уведомления |
| A-10 | Уведомление не доставлено | Заказ сохраняет результат, администратор видит проблему |
| A-11 | Покупатель открывает чужой заказ | Содержимое заказа не раскрывается |
| A-12 | Администратор пытается опустить остаток ниже резерва | Изменение отклонено; ранее подтверждённый резерв сохранён |
| A-13 | Покупатель дважды создаёт корзину, в том числе одновременно | Есть только один активный черновик; после его оформления можно создать новый |

Для демонстрации нужны исходные данные как минимум с доступным товаром,
товаром с недостаточным остатком и возможностью оставить ровно одну единицу.
Критерий готовности — все обязательные требования и сценарии A-01—A-13
выполняются на выделенном демонстрационном окружении.
Приёмка проводится HTTP-запросами и автоматическими тестами без браузера.
Инструкции описывают вход, cookie и CSRF-токен, тела запросов, HTTP-коды
и ожидаемые JSON-состояния, включая ожидание фоновой обработки.

## 10. Границы следующего этапа

Платежи, отгрузка, возвраты, внешние каналы уведомлений, промокоды, создание
товаров через API и несколько складов могут стать отдельными учебными
расширениями. Их добавление потребует собственных правил; текущий статус
`confirmed` нельзя переименовать в «оплачен» без изменения смысла процесса.

Системный анализ превращает эти требования в состояния, контракты и проверки.
План разработки должен разбить работу на небольшие рабочие этапы, каждый из
которых демонстрирует законченный результат через API.
